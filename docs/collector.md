# 租赁数据采集器设计说明

`src/collector/` 是在源站模拟器旁新增的采集模块，供多个获准站点共用。本文说明授权与数据提交如何协调、崩溃边界和取舍。运行方式见 README 的「采集器」一节。

## 模块划分

| 文件 | 职责 |
| --- | --- |
| `collector.js` | 编排：多站点共用引擎，`runOnce / runSite / refreshGrants / status / records` |
| `scan.js` | 扫描：分页遍历、详情确认、完整视图切换、断点续传 |
| `http.js` | 范围受控的请求：逐跳核对、条件请求、429 冷却、重试预算 |
| `scheduler.js` | 单站点调度：并发上限、请求间隔、限流冷却（站点间互不影响） |
| `store.js` | 持久化与授权：清单确认、撤回/字段清理、写入门控、原子落盘 |
| `robots.js` / `parse.js` / `sanitize.js` | robots 解析、HTML 定向提取、数据最小化 |
| `clock.js` | 可替换时钟：`realClock` 与测试用 `ManualClock` |
| `cli.js` | 值班入口：`start / resume / status` |

## 授权模型

每个接入配置给出准确的 `origin`、`pathPrefix`、`purpose` 和 `allowedFields`。一次请求被允许，需要同时满足：origin 与配置完全一致（域名相同不代表路径获准）、路径落在前缀内、robots.txt 放行——三者取交集，最严格的一侧生效。跳转不自动跟随：解析下一跳后重新走同一套核对，跨 origin、越前缀、被 robots 禁止或指向登录/联系页的跳转链就此终止，目标不会被请求。

授权清单（manifest）的处理规则：

- 本地持久化 `knownGrantVersion` 作为已确认边界。清单版本低于本地的一律视为重放，整体忽略；旧代次、重放响应、缓存都不能扩大授权。
- 确认较新清单时**立即**落实，先于任何后续数据提交：撤回编号从可查询视图删除，字段按「配置 ∩ 清单」收窄后的范围清理现存记录、条件请求缓存和扫描恢复材料。即使完整扫描尚未结束，撤回也已生效。
- 撤回编号以更高授权版本重新公布（不再出现在 revoked 中）时，恢复正常采集；此前的旧响应依然无权写入（见下）。
- ETag 只代表页面内容。304 响应与 200 走同一套门控，不能用来证明权限仍然有效。
- 采集器只对自己拉取并确认的清单负责，不要求感知源站尚未拉取的变化。

## 写入门控

数据只有经过 `store.commitDetail`（200）或 `store.confirmDetail`（304）才能进入可查询视图，两者都检查：

1. 编号不在本地已确认的撤回列表中；
2. 响应代次与当前活动扫描代次一致（扫描已被作废或替换时一律丢弃）；
3. 房源版本不低于现存记录（较旧版本不能覆盖新版本）；
4. 字段在提交瞬间按当前有效允许清单裁剪——而不是抓取瞬间。

因此「合作方收回房源时已排进队列的旧页面」有两道防线：确认新清单时撤回编号会从待抓队列和缓存中清除（不会发请求）；已经在途的旧响应返回时，门控按最新的本地授权状态丢弃它（不会复活记录）。

## 代次纪律与完整视图

- 扫描以清单代次为边界。任何响应的 `x-data-generation` 与扫描代次不一致，本轮立即作废：已提交的记录保留（它们是合法观察），但不做任何下架判定，随后以新清单重新开始。
- 只有清单、所有分页、所有详情同属一个代次且遍历完整（页数达到 `expectedPages`、无失败缺口），才 `finalizeScan` 切换到新的完整视图——本轮没有重新确认的编号才视为下架。
- 分页没走完、站点中途切换代次、存在失败缺口，都只记录可解释的缺口状态（`lastResult.gaps`），绝不删除记录。

## 崩溃边界与恢复

每个站点一个状态文件（`<stateDir>/<key>.json`），tmp + rename 原子替换；文件内含授权、数据集、条件请求缓存、扫描游标四类内容。检查点：确认清单后、每抓完一页、每条详情提交后都落盘。

- 在任意检查点之间崩溃：重启后读取状态文件，进行中的扫描按代次继续——已完成的页与详情不重抓，失败项重新排队。
- 崩溃发生在写文件期间：rename 保证要么旧要么新，不会出现半截文件。
- 撤回确认先于落盘后的任何提交；即使崩溃发生在「确认清单」与「扫描结束」之间，恢复后视图中的撤回依然有效（授权状态与数据集在同一原子文件里）。
- 限流、网络中断、进程退出（含 SIGKILL）都走同一条恢复路径：`cli.js resume` 或再次 `runOnce()`。

重试有次数（`maxAttempts`）和时间（`retryBudgetMs`）两份预算，429 按 `Retry-After` 冷却本站点（上限 `maxCoolingMs`），耗尽后把缺口（编号、原因、尝试次数）留在扫描游标与 `lastResult` 里。一个站点冷却不影响其他站点：调度器按站点隔离，`runOnce` 并行推进。时钟与等待通过 `clock` 注入，本地可用 `ManualClock` 无耗时重演限流与预算耗尽。

## 数据最小化

持久化文件、失败日志、异常文本只包含：来源标识、房源编号、版本、采集时间、授权依据（授权版本）、允许字段、清洗后的路径。原始 HTML 不落地（列表页只存提取出的链接，详情页只存裁剪后的字段）；联系电话、姓名等多余字段在提交前裁掉；完整 URL 的查询参数一律不落地（列表页键仅保留 `page` 参数），异常文本中的地址只保留路径部分。

## 取舍

- **单写者**：一个状态目录同一时刻只应由一个采集进程使用，没有加文件锁；多站点共用一个进程内的调度器。换简单可靠的崩溃语义，放弃多进程并发写。
- **写放大**：每条详情提交后整文件落盘。数据规模小（每站点数百条）时这是正确选择；规模上来后应换成追加日志 + 定期压实。
- **详情顺序抓取**：单站点内详情逐条处理（并发上限仍可配置，用于在途旧任务与清单刷新等控制面请求）。站点级吞吐靠多站点并行，换取确定的重试与崩溃语义。
- **定向解析**：用正则提取源站稳定的页面结构（`data-listing-id`、`data-field`、`rel="next"`），不引入 HTML 解析依赖；源站结构变化时解析会失败并把缺口记入状态，而不是静默出错数据。
- **轮询授权**：源站不推送授权变化，采集器在每轮扫描开始、详情 404、代次漂移时确认清单，并提供 `refreshGrants()` 供值班或上游回调主动触发。
- **robots 失败即停抓**：robots.txt 拉取异常时按「全部禁止」处理本轮，宁可留缺口也不越过可能存在的禁令。

## 配置项

```json
{
  "stateDir": "./.collector-state",
  "sites": [
    {
      "key": "site-a",
      "origin": "http://127.0.0.1:8080",
      "pathPrefix": "/catalog/",
      "purpose": "rental-index",
      "allowedFields": ["district", "area", "rent"],
      "requestIntervalMs": 100,
      "concurrency": 2,
      "maxAttempts": 5,
      "retryBudgetMs": 60000,
      "maxCoolingMs": 30000
    }
  ]
}
```

`key` 会作为状态文件名，只允许字母数字与连字符；`origin` 不得携带凭据与路径。清单中的 `purpose` 与配置不一致时拒绝采集。
